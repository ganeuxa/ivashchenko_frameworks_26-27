# Система учёта расходных материалов

Учебный проект: материалы, склады, остатки, приход, расход и перемещения.
В ПР9 веб-приложение переведено на Django ORM, в ПР10 добавлены админка,
статусы операций и средства анализа запросов. Консольная версия работает
с JSON независимо от сайта.

## Установка и запуск

Python 3.10+, Django 5.2, SQLite, Bootstrap 5.3, pytest, flake8.

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python manage.py migrate
python manage.py import_pr7
python manage.py runserver
```

Сайт: http://127.0.0.1:8000/. Команду `import_pr7` запускают один раз на пустых
таблицах предметной области. Если данные уже перенесены, её нужно пропустить.
Повторный запуск завершается понятной ошибкой и не изменяет данные.

## Модели и базы данных

| Модель | Поля и связи |
|---|---|
| materials.Material | id, уникальное name, unit, min_balance >= 0, уникальный slug, вычисляемый reorder_target |
| warehouses.Warehouse | id, уникальное name, необязательное location |
| warehouses.Stock | id, material → Material, warehouse → Warehouse, quantity >= 0 |
| operations.Operation | id, type, material, warehouse, необязательный target_warehouse, quantity > 0, performed_at, status (posted/cancelled/draft) |

У Stock уникальная пара (material, warehouse). Внешние ключи используют
`PROTECT`: материал или склад с остатками/историей нельзя случайно удалить.
Обратные связи: `stocks`, `operations`, `incoming_transfers`.
Склад назначения обязателен только у перемещения и отличается от отправителя;
допустимые типы операций и положительное количество проверяет база.
Даты хранятся как DateTimeField с часовым поясом Europe/Moscow.

Выбрана стратегия новой структуры: управляемые миграциями таблицы создаются
в `db.sqlite3` рядом со служебными таблицами Django. `data/consumables.sqlite`
остаётся исходной базой ПР7, открывается при переносе только для чтения.
`db/transfer.py` сохраняет идентификаторы, связи, даты, признаки отмены и
готовые остатки, не проводя операции повторно. Перенос атомарный: ошибка
отменяет все вставки. Исходные 5 материалов, 2 склада, 6 остатков и 13 операций
перенесены. Локальная база Django исключена из Git.

```powershell
python manage.py import_pr7 --source data/consumables.sqlite
python manage.py showmigrations
python manage.py sqlmigrate operations 0001
```

Старая реализация (`sql/`, `db/database.py`, `db/queries.py`,
`db/import_json.py`) сохранена для ПР7 и её тестов. Веб-представления её
не используют. Прямое чтение sqlite3 осталось только в команде переноса.
Пакет `models/` содержит обычные Python-классы консольной версии;
Django-модели находятся в `models.py` соответствующих приложений.

## Страницы и пользовательские сценарии

| Адрес | Возможности |
|---|---|
| `/` | сводка и материалы с остатком ниже минимума |
| `/materials/` | общие остатки; `?q=...` ищет по названию или единице измерения |
| `/materials/<slug>/` | остатки по складам и история материала; числовой адрес также сохранён |
| `/materials/find/` | склады, где материала не меньше заданного количества |
| `/warehouses/` | склады, включая пустые, число позиций |
| `/warehouses/<id>/` | остатки на складе и общий запас материалов |
| `/operations/` | история с поиском, фильтрами, сортировкой, пагинацией |
| `/operations/<id>/` | операция и связанные объекты |
| `/operations/statistics/` | операции по типам и складам, расход с порогом `?min=10` |

Параметры истории: `q` (материал, склад отправления или назначения), `type`
(receipt/write_off/transfer), `status` (posted/cancelled/draft), `warehouse` (любой из двух складов), `from` и
`to` (даты включительно), `hide_cancelled=1`, `sort`
(newest/oldest/material/quantity), `page`. На странице 10 записей.
Ссылки страниц сохраняют остальные GET-параметры через `{% querystring %}`.
После отправки формы фильтрации вывод начинается с первой страницы.
Недопустимая сортировка заменяется на newest по белому списку; неверный тип
игнорируется, неверная дата сопровождается сообщением. Нечисловая страница
открывает первую, отсутствующая/отрицательная — последнюю (Paginator.get_page).
Несуществующие объекты дают 404; пустые выборки отображают пояснение.
Отменённые операции не участвуют в статистике.

## ORM выражения ПР9

Запросы находятся в `db/orm.py` и `views.py` приложений. Ниже перечислены
разные законченные выражения, используемые страницами, а не отдельные вызовы
методов внутри одной цепочки.

| № | Выражение и назначение | Категория |
|---|---|---|
| 1 | Material.objects.values: варианты формы выбора | получение, сокращённые поля |
| 2 | Material.objects.filter(pk=...).first(): карточка | отдельный объект |
| 3 | Stock.filter(material_id=..., quantity__gt=0).values(...) | несколько условий, связи |
| 4 | Warehouse.filter(stocks__material_id=..., stocks__quantity__gte=...) | фильтрация связанных полей |
| 5 | Operation.filter(type=...) | одно условие |
| 6 | Operation.exclude(status=Operation.Status.CANCELLED) | исключение |
| 7 | Material.filter(Q(name__icontains=...) | Q(unit__icontains=...)) | строковый поиск |
| 8 | Operation.filter(Q(material__name__icontains=...) | Q(warehouse__name__icontains=...) | Q(target_warehouse__name__icontains=...)) | поиск нескольких полей |
| 9 | Material.annotate(total=Sum(...)).order_by(name) | сортировка одного поля, аннотация |
| 10 | Operation.order_by(performed_at, id) | сортировка нескольких полей |
| 11 | Operation.select_related(material, warehouse, target_warehouse) | связанные объекты, оптимизация |
| 12 | Stock.filter(...).values_list(material_id, quantity) | связи, сокращённые данные |
| 13 | Operation.exclude(...).aggregate(total=Count(id)) | сводный показатель |
| 14 | Operation.values(type).annotate(Count, Min, Max) | группировка |
| 15 | Paginator(rows.order_by(...), 10).get_page(...) | постраничная выборка |
| 16 | Warehouse.annotate(positions=Count(..., filter=Q(...))) | пустые склады, условный подсчёт |
| 17 | Material.annotate(consumed=Sum(...)).filter(consumed__gte=...) | расход и фильтрация групп |
| 18 | Material.annotate(total=Sum(...)).filter(total__lt=F(min_balance)) | дефицит |
| 19 | Operation.filter(performed_at__date__gte/lte=...) | диапазон дат |
| 20 | Operation.filter(Q(warehouse_id=...) | Q(target_warehouse_id=...)) | склад отправления или назначения |

Списки операций получают связанные объекты одним запросом, без дополнительных
запросов при обращении к их названиям. Для values()/values_list() соединения
строятся по указанным полям, отдельный select_related() не нужен.

## CRUD и консольная версия

```powershell
python manage.py demo_crud
python manage.py shell
```

`demo_crud` выполняет create(), get(), save(), refresh_from_db(), delete()
на демонстрационном материале внутри отменяемой транзакции. Рабочие данные
не изменяются. Это пример операций ORM для защиты ПР9. Веб-формы изменения
складского учёта в этой работе не добавлялись.

Для ручной проверки в shell:

```python
from materials.models import Material
material = Material.objects.create(name="Проверка ORM", unit="шт")
material = Material.objects.get(pk=material.pk)
material.min_balance = 3
material.save()
material.delete()
```

Удалять можно только материал без зависимых записей. Изменять состояние операции следует через `operations.services.transition()`.
Прямые create()/update() ORM предназначены для низкоуровневой работы и сами
по себе не проводят складское движение.

```powershell
python main.py
```

Консоль поддерживает приход, расход, перемещение и отмену с пересчётом
остатков и сохранением JSON. Она не синхронизируется с Django-базой.
`python -m db.import_json` обновляет только старую базу ПР7 из JSON.

## ПР10 Административная панель

```powershell
pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Адрес: http://127.0.0.1:8000/admin/. Доступ получают активные сотрудники
с нужными разрешениями или суперпользователь. Пароли и база не входят в Git.

Зарегистрированы Material, Warehouse, Stock, Operation. У приложений,
моделей и полей русские названия. Настроены list_display, search_fields,
list_filter, ordering и страницы по 20 записей. В операциях доступны
autocomplete_fields для материала и обоих складов, date_hierarchy по дате,
list_select_related. В карточках материала и склада находятся inline
остатков и истории, включая входящие перемещения. История в inline
доступна для просмотра и перехода в карточку операции.

Материалы и склады можно создавать и редактировать. Новая операция
сохраняется как черновик. В списке операций выберите строки и действие
«Провести / восстановить» либо «Отменить». Каждая операция обрабатывается
в своей атомарной транзакции: движение остатков и статус сохраняются вместе.
Частичный успех массового действия отображается количеством обработанных
записей и сообщениями об ошибках остальных. Повторное проведение/отмена
отклоняется. При недостатке материала операция не меняется, в том числе при
отмене уже израсходованного прихода или перемещения. Уменьшение остатка
выполняется условным UPDATE с F(), что не допускает отрицательных значений.

Редактировать и удалять можно только черновик; поля проведённых и отменённых
операций доступны для чтения. Остатки также доступны для чтения, меняются
через операции. Массовое удаление операций отключено. Для исправления
проведённой записи отмените её и создайте новую. Прямое редактирование
таблиц через shell не заменяет сервис проведения.

## ПР10 Статусы и миграции

`Operation.Status`: POSTED («Проведена»), CANCELLED («Отменена»),
DRAFT («Черновик»). Статусы адаптированы к складскому учёту: состояние
«завершённое бронирование» из Roomly не переносится в предметную область.
Только POSTED влияет на остатки и статистику расхода. История по умолчанию
показывает все статусы, отдельный фильтр позволяет выбрать один.

Миграция operations/0002 сначала добавляет status, затем RunPython переводит
старое is_cancelled=True в cancelled, False в posted, после чего удаляет
булево поле. Существующие остатки не пересчитываются. Обратное преобразование
сохраняет признак отмены; черновики при откате к ПР9 теряют отдельный статус.
Переход проверен на исторических моделях MigrationExecutor.

`OperationQuerySet` предоставляет posted(), cancelled(), drafts(),
with_related(), for_material(), on_date(). Менеджер создан через as_manager()
и используется в ORM-слое и представлениях. Статистика выводит общее число
операций и условные Count(..., filter=Q(...)) по трём статусам.

Доступность материала определяется текущим остатком, а не наличием операции
на определённую дату. Черновик расхода её не уменьшает; проведение уменьшает,
отмена восстанавливает. Это проверяется на одном материале и количестве.

## ПР10 Адреса и общие данные

У материала уникальный англоязычный slug. Unidecode транслитерирует название,
slugify нормализует его. Миграция materials/0003 заполняет существующие
материалы строкой «название-id», затем включает уникальность. Для новых
материалов save() подбирает свободный суффикс. После переименования slug
сохраняется. Прямой bulk_create() материалов обходит save(), поэтому при
таком использовании slug нужно передать явно.

get_absolute_url() возвращает адрес /materials/<slug>/; список материалов
и кнопка Admin «Смотреть на сайте» используют его маршрут. Прежние числовые
адреса продолжают работать. Неизвестный slug даёт 404.

GeneratedField reorder_target вычисляется базой как min_balance * 2:
учебный целевой запас для пополнения. После изменения минимума значение
обновляется при refresh_from_db(). Поле не редактируется вручную, отображается
в карточке и админке. Контекстный процессор homepage.context_processors.site_info
передаёт название сайта и число материалов в общий подвал страниц.

## ПР10 Анализ SQL

Django Debug Toolbar 8.0.0 подключён только при DEBUG=True вне тестов.
Панель доступна с локального адреса (INTERNAL_IPS), маршруты подключаются
через debug_toolbar_urls(). Для отключения задайте DEBUG_TOOLBAR=0 перед
запуском сервера. Установка: https://django-debug-toolbar.readthedocs.io/en/stable/installation.html.

Фактическая проверка в браузере, без авторизации пользователя:

| Страница | SQL-запросы | Назначение |
|---|---:|---|
| История операций | 4 | COUNT пагинации, COUNT общего подвала, склады фильтра, текущая страница с JOIN и LIMIT |
| Вторая страница с status=posted и sort=oldest | 4 | те же запросы с WHERE, ORDER BY, LIMIT/OFFSET |
| Карточка операции | 2 | объект со связями через JOIN, COUNT общего подвала |

Запрос данных операции соединяет материал и склад через INNER JOIN,
необязательный склад назначения через LEFT OUTER JOIN. Обращения к именам
не создают дополнительных запросов. После входа могут добавиться запросы
сессии и пользователя. Тест CaptureQueriesContext подтверждает, что число
запросов списка Admin не растёт при добавлении операций.

Скриншоты реального интерфейса и SQL сохранены локально в
`Отчёты/ПР10_скриншоты/`; отчёт ПР10 находится рядом. Эта папка исключена
пользовательскими настройками Git. Резервная копия базы перед миграцией
сохранена в `.pytest_cache/backups/` и также не включается в коммит.
