# Система учёта расходных материалов

Приложение для учёта расходных материалов по складам: приход, расход,
перемещение и контроль остатков. Есть консольная версия и веб-интерфейс на
Django, который пока показывает данные (менять их можно через консоль).

## Технологии

- Python 3.10+;
- Django 5.2, веб-фреймворк;
- шаблоны Django (Django Template Language);
- HTML, Bootstrap 5.3 (через CDN), свой CSS и немного JavaScript;
- JSON-файлы для хранения данных;
- pytest и flake8 для тестов и проверки кода.

## Назначение

Приложение ведёт учёт расходных материалов: что есть в наличии, на каком складе
лежит и сколько осталось. Каждый приход и расход записывается как операция.
Программа не даст списать больше, чем есть на складе, и предупредит, когда
материал пора докупать.

## Целевая аудитория

Кладовщики, которые принимают и выдают материалы. Сотрудники хозотдела и
снабжения: им нужно видеть остатки, чтобы вовремя заказывать новое. Руководители
подразделений, которым интересно, сколько тратит их отдел.

## Предметная область

В любом офисе, колледже или мастерской постоянно уходят бумага, картриджи,
канцелярия, моющие средства, мелкие запчасти. Всё это хранится на одном или
нескольких складах. Когда материал привозят, оформляют приход, и остаток растёт.
Когда выдают, оформляют расход, и остаток уменьшается. У каждого материала есть
минимальный остаток: если на всех складах вместе осталось меньше, материал надо
дозаказать.

## Основные сущности

- Материал: наименование, единица измерения, минимальный остаток.
- Склад: название и где он находится.
- Операция: приход, расход или перемещение, материал, склад, количество и дата.
- Остаток: сколько единиц материала сейчас лежит на конкретном складе.

## Возможности

В консольной версии:

- просмотр списка материалов с общим остатком и статусом;
- поиск материала по части названия;
- добавление материалов и складов;
- просмотр остатков на выбранном складе;
- приход материала на склад;
- расход с проверкой, хватает ли материала;
- перемещение материала между складами;
- история операций и отмена операции с пересчётом остатков
  (отменённая операция остаётся в истории с пометкой);
- список материалов, которые пора дозаказать.

Все изменения сразу сохраняются в JSON-файлы, так что после перезапуска данные
остаются. Неправильный ввод (буква вместо числа, несуществующий номер) и битые
файлы данных программу не роняют.

В веб-интерфейсе пока только просмотр: списки и карточки материалов, складов и
операций, статусы остатков. Добавление и изменение через браузер появится,
когда пройдём модели и формы Django.

## Страницы веб-интерфейса

| Адрес | View-функция | Что показывает |
|---|---|---|
| `/` | `homepage.views.index` | главная: что пора дозаказать, со шкалами остатков |
| `/materials/` | `materials.views.materials` | ведомость материалов: шкала остатка, количество, статус |
| `/materials/<int:material_id>/` | `materials.views.material_detail` | карточка материала: остатки по складам и его операции |
| `/warehouses/` | `warehouses.views.warehouses` | список складов |
| `/warehouses/<int:warehouse_id>/` | `warehouses.views.warehouse_detail` | что лежит на складе |
| `/operations/` | `operations.views.operations` | история операций, новые сверху, можно скрыть отменённые |
| `/operations/<int:operation_id>/` | `operations.views.operation_detail` | карточка операции |

Если материала, склада или операции с таким номером нет, view-функция
возвращает страницу «не найдено» с кодом 404. Для адресов, которых нет вообще,
в `consumables/urls.py` подключён `handler404`, он показывает свою страницу 404
(видно при `DEBUG = False`). Адрес вроде `/materials/abc/` тоже даёт 404: конвертер
`<int:...>` пропускает только числа.

View-функции ничего не считают сами и не собирают HTML. Они загружают данные
через `load_data()` из `storage.py`, находят нужный объект функциями из пакета
`models`, складывают всё в словарь `context` и вызывают `render()` с нужным
шаблоном. HTML целиком лежит в шаблонах.

## Шаблоны

Общий каркас всех страниц лежит в `templates/base.html`: `<head>` с Bootstrap и
своим CSS, меню, подвал и подключение скрипта. В нём два блока,
`{% block title %}` и `{% block content %}`, остальные шаблоны начинаются с
`{% extends "base.html" %}` и переопределяют только их.

Повторяющиеся куски вынесены в отдельные файлы и подключаются через
`{% include %}`:

- `templates/includes/navigation.html`: шапка с меню, текущий раздел
  подсвечивается через `request.resolver_match.app_name`;
- `templates/includes/stock_badge.html`: метка статуса остатка («в норме»,
  «ниже минимума», «закончился»). Нужна и материалам, и складам, поэтому лежит
  на уровне проекта и получает уровень через `with level=...`;
- `templates/includes/stock_gauge.html`: шкала остатка, полоса заполнения с
  засечкой на уровне минимума;
- `materials/includes/material_row.html`: строка материала в ведомости, её же
  использует главная;
- `warehouses/includes/warehouse_item.html`: строка склада;
- `operations/includes/operation_qty.html`: количество со знаком (`+40` для
  прихода, `−5` для расхода, `⇄` для перемещения);
- `operations/includes/operation_status.html`: «проведена» или «отменена».

Что используется внутри шаблонов:

- `{{ ... }}` для атрибутов объектов: `{{ material.name }}`,
  `{{ operation.material.unit }}`;
- `{% for %}` с `{% empty %}` для списков, на пустом списке выводится
  «Материалов пока нет» и подобное;
- `{% if %}` для статусов и для страниц «не найдено»: если объекта нет, view
  передаёт в шаблон `None`, шаблон показывает сообщение, а `render()`
  вызывается со `status=404`;
- фильтры: `|length` (сколько материалов, складов, операций), `|default` (имя
  или адрес, если пустые), `|date:"d.m.Y H:i"` для дат операций, `|lower`.

Уровень остатка (`empty`, `low`, `ok`) и ширину шкалы считает функция
`summarize_material()` в `models/stock.py`, а не шаблон: решать, что считать
«мало», это логика предметной области. Шкала берёт за 100% удвоенный минимум
(или сам остаток, если он больше), поэтому засечка минимума обычно стоит
посередине. Шаблон только подставляет готовые числа и выбирает цвет. Для фильтра `date`
у операции есть свойство `performed_at`, оно превращает строку даты из JSON в
`datetime`.

## Маршруты

У каждого приложения в `urls.py` задано своё пространство имён `app_name`, а у
маршрутов имена `list` и `detail`. Ссылки в шаблонах строятся только через
`{% url %}`, без адресов вручную:

```
{% url 'homepage:index' %}
{% url 'materials:list' %}      {% url 'materials:detail' material.id %}
{% url 'warehouses:list' %}     {% url 'warehouses:detail' warehouse.id %}
{% url 'operations:list' %}     {% url 'operations:detail' operation.id %}
```

## Статические файлы

Лежат в `homepage/static/homepage/` и подключаются в `base.html` через
`{% load static %}` и `{% static '...' %}`:

- `css/style.css`: всё оформление проекта. Цвета заданы переменными в
  `:root` (стальной синий, сигнальный жёлтый для «мало», красный для
  «закончился»), шрифт Golos Text, ведомость материалов, шкалы остатков,
  таблицы операций, мобильная вёрстка;
- `js/main.js`: ставит текущий год в подвал и по галочке на странице операций
  скрывает отменённые;
- `img/logo.svg`: логотип в шапке.

Bootstrap подключён и даёт базовый сброс стилей и отступы, но внешний вид
страниц задаёт свой CSS.

## Классы

Материал, склад, остаток и операция описаны классами в пакете `models`.

### Material, материал

Атрибуты: `id`, `name`, `unit` (единица измерения), `min_balance`
(минимальный остаток).

Методы:
- `needs_reorder(total)` говорит, пора ли дозаказывать при таком остатке;
- `validate_min_balance()` (`@staticmethod`) проверяет, что минимум не меньше
  нуля, конструктор пользуется ей сам;
- `from_data()` (`@classmethod`) и `to_data()` переводят материал из записи
  JSON и обратно;
- `__str__()` выдаёт «Бумага офисная А4 (пачка)».

### Warehouse, склад

Атрибуты: `id`, `name`, `location`. Методы `from_data()`, `to_data()`,
`__str__()`.

### StockItem, остаток

Хранит ссылки на объекты `Material` и `Warehouse` и количество. Количество
лежит в закрытом атрибуте `_quantity`, снаружи его можно только прочитать через
свойство `quantity`. Менять остаток можно методами `add()` и `remove()`, и
`remove()` не даст уйти в минус. Метод `can_write_off()` проверяет, хватает ли
материала. Раньше это была отдельная функция из ПР1.

### Operation и наследники

`Operation` общий класс операции: номер, материал, склад, количество, дата и
признак `is_cancelled`. От него наследуются три вида:

- `Receipt`, приход;
- `WriteOff`, расход;
- `Transfer`, перемещение, у него есть ещё `target_warehouse`.

Каждый наследник по-своему реализует `apply()` (провести операцию по остаткам)
и `revert()` (вернуть как было). Общий метод `cancel()` вызывает `revert()`
нужного класса и ставит `is_cancelled`, саму операцию из истории не удаляет.
`Transfer` дополнительно переопределяет `place()`, `to_data()` и проверку в
конструкторе, что склады разные.

### Как объекты связаны

`StockItem` и `Operation` хранят сами объекты `Material` и `Warehouse`, а не
номера. Поэтому из операции можно сразу взять `operation.material.name` или
`operation.warehouse.name`. В JSON же пишутся только номера: при сохранении
`to_data()` подставляет `material.id`, а при загрузке `storage.py` по номерам
находит уже загруженные объекты и связывает их обратно. Если номер ни на что не
указывает, запись пропускается.

Функции, которые работают со списками объектов (поиск, сортировка, подсчёт
общего остатка, оформление операций), остались обычными функциями в тех же
модулях. Загрузка и сохранение тоже обычные функции в `storage.py`.

В `main.py` есть декоратор `saves_data`: им помечены пункты меню, которые
меняют данные, и после успешного действия он сам сохраняет всё в JSON.

## Структура проекта

```
manage.py            команды Django: runserver, check, migrate
consumables/         настройки Django-проекта
    settings.py      настройки, список приложений, язык и часовой пояс
    urls.py          корневые маршруты и handler404
templates/           шаблоны уровня проекта
    base.html        общий каркас страниц
    includes/        меню и бейдж статуса остатка
homepage/            главная и страница 404
    templates/       index.html, 404.html
    static/          CSS, JS и логотип
materials/           страницы материалов: views.py, urls.py, templates/
warehouses/          страницы складов
operations/          страницы операций
main.py              консольная версия: меню и вывод на экран
models/
    __init__.py      импорт классов из пакета
    materials.py     класс Material и функции поиска и сортировки
    warehouses.py    класс Warehouse
    stock.py         класс StockItem, подсчёт остатков, что дозаказать
    operations.py    классы операций, оформление и отмена
storage.py           загрузка и сохранение JSON
utils.py             ввод чисел и строк с проверкой, номера, дата
data/                файлы с данными
tests/               тесты pytest
```

`models/` это наши классы предметной области из ПР3. Не путать с файлами
`models.py` внутри Django-приложений: они пока пустые. Данные по-прежнему
хранятся в JSON, Django ORM и база данных пока не используются, форм тоже ещё
нет. Это следующие практические работы.

## Формат данных

Данные лежат в папке `data/`, в каждом файле список записей.

`materials.json`:

```json
[{"id": 1, "name": "Бумага офисная А4", "unit": "пачка", "min_balance": 10}]
```

`warehouses.json`:

```json
[{"id": 1, "name": "Склад №1", "location": "корпус А, 1 этаж"}]
```

`stock.json`, один остаток на пару «материал, склад»:

```json
[{"material_id": 1, "warehouse_id": 1, "quantity": 40}]
```

`operations.json`, тип операции бывает `receipt` (приход), `write_off` (расход)
и `transfer` (перемещение, тогда заполнен `target_warehouse_id`). По типу при
загрузке выбирается класс `Receipt`, `WriteOff` или `Transfer`:

```json
[{"id": 1, "type": "receipt", "material_id": 1, "warehouse_id": 1,
  "target_warehouse_id": null, "quantity": 40, "date": "2026-09-01 10:15",
  "is_cancelled": false}]
```

В программе всё это списки объектов: `list[Material]`, `list[Warehouse]`,
`list[StockItem]`, `list[Operation]`.

## Требования

- Python 3.10 или новее;
- Django 5.2;
- pytest и flake8 (только для разработки).

Всё перечислено в `requirements.txt`.

Установка:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

## Запуск

Веб-версия. Перед первым запуском нужно применить служебные миграции Django:

```bash
python manage.py migrate
python manage.py runserver
```

После этого открыть http://127.0.0.1:8000/ в браузере. Проверить настройки без
запуска сервера можно командой `python manage.py check`.

Консольная версия:

```bash
python main.py
```

## Запуск тестов

```bash
pytest -v
```

Тесты проверяют создание объектов и их атрибуты, `__str__`, то, что остаток
нельзя поменять напрямую и увести в минус, приход, расход, перемещение, отмену
операций, а ещё то, что после сохранения и загрузки связи между объектами
восстанавливаются. `tests/test_web.py` открывает страницы через тестовый
клиент Django на отдельных тестовых данных и проверяет, что каждая страница
собрана из своего шаблона и `base.html`, коды ответа 200 и 404, работу
фильтров, пустые списки, отменённую операцию и свою страницу 404.
